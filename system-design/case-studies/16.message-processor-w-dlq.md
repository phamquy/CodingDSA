#### **Design #4: Message Processor with DLQ + Retry**

This document designs a high-throughput message processing system with **retries**, **dead-letter queue (DLQ)**, **out-of-order handling**, and **exactly-once semantics** (at the business-effect level). It targets an audience unfamiliar with messaging systems and explains the rationale and trade-offs behind key choices.

---

### 1) Problem statement

We receive events from a broker (e.g., Kafka / SQS / PubSub) and must process them reliably:
- Apply business logic (e.g., update a record, call downstream services, emit derived events)
- Handle failures with retries
- Isolate poisonous messages via DLQ
- Tolerate duplicates and out-of-order delivery

The core challenge: most brokers provide **at-least-once** delivery, not true exactly-once end-to-end. We need to build correctness using **idempotency**, **deduplication**, and careful commit semantics.

---

### 2) Functional requirements

- Consume messages from a topic/queue.
- Process each message and produce side effects (DB writes, downstream calls, new events).
- Provide **exactly-once semantics** for business outcomes (no double charge, no double state transition).
- Handle **out-of-order** events per entity.
- Support **redelivery behavior**: backoff retries, max attempts, and eventual DLQ.
- Provide **failure isolation** so a bad message doesn’t stall the whole system.

---

### 3) Non-functional requirements

- High availability and horizontal scalability.
- Predictable latency (bounded retry behavior).
- Operable: metrics, tracing, alerting, replay tooling.
- Cost effective: avoid hot partitions and thundering herds during retries.

---

### 4) Scope and assumptions

Assume:
- Messages include a stable `message_id` (UUID) and an `entity_id` (e.g., order_id, user_id).
- Messages may be duplicated and may arrive out of order.
- We have a primary datastore that supports conditional updates / transactions.

Out of scope:
- The producer’s reliability guarantees.
- Full schema registry governance (we’ll mention compatibility).

---

### 5) Architecture overview

**Core components**
- **Message broker**: source of events.
- **Processor workers** (stateless): consume → validate → dedupe/order → execute → commit/ack.
- **Idempotency store**: records processed `message_id` (and optionally outcome hash) to prevent duplicates.
- **State store** (business DB): durable state transitions.
- **Retry scheduler**: manages delayed retries (via delay queue, scheduled messages, or retry topics).
- **DLQ**: holds messages that exceeded retry budget or are non-retriable.
- **Observability pipeline**: metrics + structured logs + traces.

Key design principle:
- Treat the broker as **at-least-once**, and build correctness via **idempotent effects** + **atomic commit patterns**.

---

### 6) Message model

Minimum envelope (illustrative):
- `message_id`: unique id for dedupe
- `entity_id`: ordering key
- `event_type` + `payload`
- `event_time`: producer timestamp
- `version` or `sequence`: monotonic per entity (preferred)
- `attempt`: retry attempt count (added by retry mechanism)

Rationale:
- Exactly-once and ordering are significantly simpler when we have a per-entity monotonic `sequence`.
- If sequence is unavailable, we fall back to event-time + conflict resolution (weaker guarantees).

---

### 7) Processing flow (hot path)

The worker processes each message through staged gates:

#### Step A — Validate and classify
- Validate schema and required fields.
- Classify errors:
	- **Non-retriable**: invalid schema, unsupported version, failed auth → DLQ directly.
	- **Retriable**: transient network errors, 5xx from dependencies → retry.

Trade-off:
- Aggressive DLQ on validation reduces wasted retries, but risks dropping messages if schema validation is too strict during rollouts.

#### Step B — Dedupe / idempotency (exactly-once)

Goal: ensure the business effect of a message is applied once.

Common approaches:
1) **Idempotency key table** (recommended)
	 - Write a row keyed by `message_id` when processing succeeds.
	 - If `message_id` already exists, treat as duplicate and skip work.
2) **Idempotent business writes**
	 - Use conditional updates keyed by `entity_id` and `sequence`.
3) Broker-native exactly-once (Kafka EOS)
	 - Works only within Kafka transactional boundaries; still needs idempotent downstream effects.

Recommended pattern (generalizable across brokers):
- Use a DB transaction that:
	- checks/creates `processed_messages(message_id)`
	- applies business state change
	- commits

This provides exactly-once for DB effects even under redelivery.

Trade-offs:
- Idempotency table increases write load; mitigate via TTL/partitioning and only storing what’s necessary.
- Hashing the payload into the idempotency record can detect inconsistent duplicates, but adds complexity.

#### Step C — Out-of-order handling

There are three common strategies; which one we choose depends on product semantics.

**Option 1: Enforce per-entity ordering using broker partitioning (preferred when possible)**
- Partition/route messages by `entity_id`.
- A single consumer group processes partitions in order.
- Out-of-order then occurs mainly across partitions, which we don’t allow for the same entity.

Trade-off:
- Ordering is achieved by limiting concurrency per entity; can reduce throughput if keys are skewed.

**Option 2: Sequence-based state machine (robust)**
- Store `last_applied_sequence` per `entity_id`.
- If message.sequence == last+1 → apply.
- If message.sequence <= last → duplicate/stale → skip.
- If message.sequence > last+1 → gap detected → buffer/defer.

Buffering approaches for gaps:
- Put message into a **deferred queue** (or retry with special reason) and try again later.
- Maintain a small per-entity in-memory buffer with eviction (careful: crash loses buffer).

Trade-offs:
- Buffering increases complexity and may increase end-to-end latency.
- Requires producers to generate monotonic sequences.

**Option 3: Commutative / conflict-resolution updates (weak ordering)**
- If operations are commutative (e.g., add-to-set) or can be merged, ordering matters less.
- Use event_time only for conflict resolution.

Trade-off:
- Simpler infra but correctness depends on business logic; not suitable for strict workflows.

#### Step D — Execute business logic
- Perform DB writes and/or call downstream services.
- Prefer **outbox pattern** for emitting derived events.

Outbox rationale:
- If we update DB and publish an event, we want atomicity.
- With an outbox, we write the outgoing event to `outbox` table in the same DB transaction, then an async publisher sends it to the broker.

Trade-offs:
- Adds a separate publisher component and operational work.
- Greatly improves reliability and avoids “DB updated but event not emitted”.

#### Step E — Commit/ack

Ack/commit strategy depends on the broker:
- Kafka: commit offset only after successful processing (and after DB commit).
- SQS/PubSub: ack only after success.

If we crash after DB commit but before ack, the broker redelivers, and idempotency logic ensures we skip.

### 8) Redelivery behavior (retries)

Retry policy must be explicit and bounded.

**Classification**
- Retriable: timeouts, connection errors, dependency 5xx, rate limits.
- Non-retriable: schema invalid, auth failure, invariant violation.

**Backoff**
- Exponential backoff with jitter.
- Example schedule: 1s, 5s, 30s, 2m, 10m, 30m.

**Max attempts**
- After N attempts (e.g., 5–10 depending on SLA), send to DLQ.

**How to implement delayed retries**
- Kafka-style: retry topics with increasing delay and consumer that re-publishes after delay.
- Queue-style: broker-native delayed message (if supported), or an external scheduler.

Trade-offs:
- Immediate retries can cause hot loops and amplify outages.
- Delayed retries reduce pressure but increase time-to-recovery.

---

### 9) Dead-letter queue (DLQ)

DLQ is for messages that cannot be processed automatically.

**When to DLQ**
- Non-retriable errors.
- Exceeded retry budget.
- Poison messages that repeatedly cause crashes or deterministic failures.

**What to store in DLQ**
- Original payload + headers
- Error classification and stack trace summary
- Attempt count and first-seen timestamp
- Processor version (helps debugging rollouts)

**DLQ operations**
- Dashboard: DLQ volume by error reason.
- Replay tool:
	- optionally patch/fix payload
	- replay back to main topic or a special “replay” topic
- Quarantine rules: prevent repeated re-DLQ loops.

Trade-offs:
- DLQ prevents whole pipeline blockage but introduces operational burden.
- Replay must respect idempotency; otherwise replaying can duplicate side effects.

---

### 10) Failure isolation

We want one bad message (or a broken dependency) to degrade gracefully, not take down the fleet.

Mechanisms:
- **Consumer parallelism**: multiple partitions/queues with independent workers.
- **Circuit breakers** for downstream dependencies.
- **Bulkheads**: limit concurrency per dependency (separate thread pools/async semaphores).
- **Poison pill isolation**: fast-path to DLQ for deterministic failures.
- **Rate limiting** to protect downstream services.

Trade-offs:
- Bulkheads add complexity but prevent cascading failures.

---

### 11) Scaling and partitioning

Scaling knobs:
- Increase consumer group size / worker replicas.
- Partition by `entity_id` to preserve ordering.

Hot key risk:
- If one entity_id is extremely frequent, a single partition becomes hot.
Mitigations:
- Reduce per-entity ordering scope if business allows (e.g., order_id vs user_id).
- Split by sub-key (only if ordering can be relaxed).

---

### 12) Observability

Must-have metrics:
- Throughput: messages/sec consumed and processed
- Lag/backlog (Kafka lag or queue depth)
- Success/failure rates by error class
- Retry counts and retry age distribution
- DLQ rate and DLQ reasons
- Processing latency (end-to-end and per stage)

Tracing/logging:
- Correlation id from message headers.
- Sample traces to keep overhead low.
- Structured logs for failure classification.

Alerts:
- DLQ spike
- sustained lag growth
- retry storm
- dependency error rate

---

### 13) Exactly-once semantics: what we guarantee (and what we don’t)

It’s important to define exactly-once precisely.

**We guarantee**
- Business state in our DB is updated exactly once per `message_id` (idempotency + transaction).

**We do not magically guarantee**
- Exactly-once effects in external systems that do not support idempotency.

For external calls, we do one of:
- Make the external call idempotent using an idempotency key.
- Move the external call behind an outbox + dedicated dispatcher with idempotency.

---

### 14) Concrete trade-offs summary

- **At-least-once broker + idempotency** is the most portable “exactly-once” approach.
- Enforcing per-entity ordering via partitioning is simplest, but can reduce concurrency with skewed keys.
- Retry with backoff prevents outage amplification, but increases time-to-final-processing.
- DLQ improves system health but requires clear replay and operational ownership.

---

### 15) Clarifying questions (what I’d ask)

- Which broker are we using (Kafka vs queue)?
- Do we require strict per-entity ordering, and what is the ordering key?
- What’s the maximum acceptable processing delay for retries?
- Are downstream side effects idempotent (or can we make them idempotent)?
- What are the expected QPS and payload sizes?
