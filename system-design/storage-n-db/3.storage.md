# Categories of Storage Systems


In this article we will look at the broad view of storage systems, from a very familiar file system to 
specialized databases designed for specific use cases. Understanding the different types of storage systems and their characteristics is crucial for designing scalable and efficient applications.

Before diving in to each storage system, let examine how data store, from very abstracted layer down to actual hardware device a bit written

## Storage System Layer Stack

**Physical Media**
- Raw hardware where bits are stored
- Examples: HDD (magnetic disks), SSD/NVMe, tape, optical media

At this lowest abstraction layer, data are bits. Bits stored in some organized structure depending physical device :

*HDD (magnetic disks)*: Bits stored as magnetic orientations on spinning platters divided into tracks, sectors, and clusters. Each bit represents magnetic polarity (north/south = 1/0)

*SSD/NVMe*: Bits stored as electrical charges in NAND flash memory cells arranged in pages, blocks, and planes. Charge presence/absence represents 1/0

*Tape*: Sequential magnetic storage where bits are stored as magnetic patterns along linear tracks on magnetic tape

*Optical media*: Bits stored as microscopic pits and lands on reflective surfaces, read by laser reflection patterns

We don't go into detail what of each structure, but the take aways here is they don't just write in a single block of data. The structure also dictate how data writen and read to and from the device. For example, data will be read/write from device one "block" at a time, the block here can be a cluster, a pages...Because of that depend on data written/red from disk, the number of device access will vary. The upper layer should optimize by align the read/write to limit number of access and also not to waste storage space.


**Device Firmware / Controller**
- Manages low-level operations like wear leveling, error correction, block mapping
- Examples: SSD controller firmware, HDD firmware

At this layer, the controller takes simple read/write commands and translates them into the precise physical operations needed on the media. It handles bad block remapping, error detection/correction, wear leveling, caching, command queueing, garbage collection, and other device-specific quirks. To the layer above (block layer / device driver), it exposes a clean, reliable, block-addressable device with a fixed logical sector size and consistent error semantics, hiding most of the complexity and unreliability of the raw media.


**Block Layer / Device Driver**
- OS-level abstraction of storage devices as block-addressable units
- Examples: Linux block device driver, NVMe driver

This layer takes the logical block device exported by the controller and integrates it into the operating system. It provides a uniform interface (e.g., `/dev/sdX`, `/dev/nvmeXnY`) regardless of the underlying hardware, handles queues and scheduling of I/O requests, enforces access permissions, and reports standardized errors and statistics. To upper layers like filesystems and volume managers, it looks like a generic block device with a known sector size, I/O APIs (read/write/ioctl), and performance characteristics, hiding vendor-specific protocols and device details.

**Volume Management / Virtualization**
- Abstracts multiple devices into logical volumes, adds redundancy or striping
- Examples: LVM, RAID, ZFS pools

This layer sits between raw devices and filesystems, combining one or more physical block devices into logical volumes. It can provide RAID (mirroring, striping, parity), snapshots, resizing, and tiering, and it tracks the mapping from logical block addresses to physical devices/offsets. To filesystems above, it looks like a single large, reliable block device, hiding the complexity of multiple disks, redundancy schemes, and layout decisions.

**Filesystem Layer**
- Provides hierarchical organization, metadata, and access semantics
- Examples: ext4, NTFS, XFS, ZFS

The filesystem takes a generic block device and turns it into a tree of files and directories with names, permissions, and metadata (size, ownership, timestamps). It decides how to lay out inodes and data blocks, manages free space, handles caching and journaling, and enforces access semantics (POSIX, ACLs, etc.). To upper layers, it exposes a path-based API (`open`, `read`, `write`, `rename`, etc.) and hides the details of how bytes are packed into sectors on disk.

**Object / Key-Value Storage**
- Abstracts data into objects or key-value pairs, hides block/filesystem details
- Examples: Amazon S3, Ceph, MinIO, RocksDB

Object and key-value stores build on top of filesystems or raw block devices to present a much simpler abstraction: store and retrieve opaque blobs by key or object ID. They handle sharding, replication, versioning, and background compaction/garbage collection. To applications, they expose HTTP/GRPC/SDK APIs (`PUT/GET/DELETE` by key) and hide concerns like file layouts, volumes, and disk failures, often spanning many machines and regions.

**Database Layer**
- Adds schema, query language, transactions, indexing
- Examples: PostgreSQL, MySQL, MongoDB

Databases use files, block devices, or KV engines underneath but add rich semantics: schemas, secondary indexes, query planners, and transactional guarantees (ACID or variants). They manage record layouts, B-trees, WAL logs, locks, and concurrency control internally. To applications, they expose a declarative query interface (SQL or document/graph queries) and transactional APIs, so callers think in terms of rows/documents and queries instead of pages, files, or keys.

**Application / Workflow Layer**
- Consumes storage through APIs, integrates with business logic
- Examples: ML pipelines (Feast, DVC), enterprise apps, ad tech platforms

At the top, applications and workflows orchestrate multiple storage systems (DBs, caches, object stores, queues) to implement business logic, data flows, and SLAs. They add domain models, validation, caching policies, and retry/compensation logic. To end users and other services, they expose high-level APIs and UIs (e.g., “create campaign”, “fetch user profile”) that completely hide the choice and structure of the underlying storage technologies.

**Notes on Abstraction**
- Each layer adds **metadata, semantics, and guarantees** (durability, consistency, replication).
- Layers can be **collapsed or bypassed** (e.g., DB on raw block devices).
- Distributed systems often **reimplement layers** (Ceph provides block, object, and filesystem).
- Performance tuning requires understanding **cross-layer interactions**.

**How to Think About It**
- **Primitive layers**: physics and reliability (bit flips, wear, latency).
- **Middle layers**: abstraction and efficiency (block mapping, file hierarchies).
- **Abstract layers**: semantics and usability (transactions, queries, APIs).

---

## 1. File Storage (File Systems)
- Stores: Files and directories
- Access: Path-based
- Examples: ext4, NTFS, APFS, NFS, SMB, HDFS, CephFS, EFS, Filestore
- Use cases: Shared files, media assets, backups




---

## 2. Object Storage
- Stores: Objects (data + metadata + ID)
- Access: Key / URL (REST APIs)
- Examples: Amazon S3, Google Cloud Storage, Azure Blob, MinIO
- Use cases: Data lakes, backups, media, ML datasets

---

## 3. Block Storage
- Stores: Raw blocks
- Access: Block device
- Examples: AWS EBS, Google Persistent Disk, Azure Disk, SAN/iSCSI
- Use cases: VM disks, databases, low-latency storage

---

## 4. Relational Databases (RDBMS)
- Stores: Tables with fixed schema
- Access: SQL + ACID transactions
- Examples: PostgreSQL, MySQL, Oracle, SQL Server, Aurora
- Use cases: OLTP, strong consistency, joins

---

## 5. Key–Value Stores
- Stores: Key → Value
- Access: Direct key lookup
- Examples: Redis, DynamoDB, etcd, FoundationDB
- Use cases: Caching, sessions, metadata

---

## 6. Wide-Column / Column-Family Stores
- Stores: Rows with dynamic columns
- Access: Row key + column family
- Examples: Bigtable, Cassandra, HBase
- Use cases: Time-series, high-write workloads

---

## 7. Document Databases
- Stores: JSON / BSON documents
- Access: Document queries
- Examples: MongoDB, Couchbase, Firestore
- Use cases: Semi-structured data, APIs

---

## 8. Graph Databases
- Stores: Nodes and edges
- Access: Graph traversal queries
- Examples: Neo4j, Neptune, JanusGraph
- Use cases: Recommendations, social graphs

---

## 9. Time-Series Databases
- Stores: Timestamped metrics/events
- Access: Time-based queries
- Examples: InfluxDB, TimescaleDB, Prometheus
- Use cases: Monitoring, IoT, metrics

---

## 10. Search / Index Stores
- Stores: Inverted indexes, Vectors DB
- Access: Full-text search queries
- Examples: Elasticsearch, OpenSearch, Solr
- Use cases: Search, log analytics

---

## 11. Data Warehouses / OLAP Stores
- Stores: Columnar analytical data
- Access: Analytical SQL
- Examples: BigQuery, Snowflake, Redshift, ClickHouse
- Use cases: BI, reporting, analytics

---

## 12. Stream / Log Storage
- Stores: Append-only event logs
- Access: Sequential reads
- Examples: Kafka, Pulsar, Kinesis
- Use cases: Event sourcing, stream processing

---

## 13. In-Memory Storage
- Stores: Volatile memory
- Access: Key-based
- Examples: Redis, Memcached
- Use cases: Caching, rate limiting

---

## 14. Backup / Archive Storage
- Stores: Cold, long-term data
- Access: Infrequent retrieval
- Examples: Glacier, Coldline, Tape
- Use cases: Compliance, disaster recovery
